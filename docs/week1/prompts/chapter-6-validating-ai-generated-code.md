## Section 6.1 — Risks of AI-Generated Implementation

Explain important risks such as:

- inventing nonexistent APIs or package behavior
- misunderstanding repository architecture
- violating an existing interface or contract
- generating code that compiles but implements the wrong behavior
- producing incomplete validation
- handling only the successful path
- losing existing data during file updates
- converting errors into false success
- incorrect asynchronous behavior
- unsafe assumptions about paths or operating systems
- unnecessary complexity
- speculative features that were not requested
- insecure or unsuitable error handling
- stale assumptions about dependencies
- inconsistent naming or domain models

Connect these risks to the Ticket Manager CLI.

Examples may include:

- accepting a blank ticket title
- assigning the wrong initial status
- treating malformed and unknown IDs as the same condition
- returning success after JSON persistence fails
- overwriting unrelated tickets during update
- silently replacing corrupted JSON
- writing to real user data during tests
- printing an error but returning success semantics
- implementing an undocumented status transition

Do not claim that these failures always occur.

## Section 6.2 — Tests as Executable Validation

Explain that a test converts an intended behavior into executable evidence.

Describe how tests can validate AI-generated code by:

1. defining the required behavior before accepting implementation
2. observing an expected Red failure
3. applying the AI-generated implementation
4. rerunning the focused test
5. running relevant regression tests
6. checking broader boundaries when the risk requires them
7. reviewing the actual failure and passing evidence
8. rejecting code that passes an irrelevant or weak test

Explain that different tests provide different evidence:

- unit tests validate focused logic
- integration tests validate real JSON and file-system behavior
- end-to-end tests validate selected public CLI journeys

A passing fake-repository test must not be described as evidence of real JSON
persistence.

Include one concise conceptual example showing how a test catches an
AI-generated implementation defect.

The example may use a proposed implementation that:

- checks `title.length` before trimming; or
- reports success before persistence completes; or
- updates one ticket by replacing the entire collection incorrectly.

Clearly label the code as conceptual and unexecuted.

## Section 6.3 — Reviewing AI-Generated Tests

Explain that AI-generated tests themselves require review.

Review criteria should include:

- Does the test represent the actual requirement?
- Would the test fail if the behavior were missing?
- Did Red fail for the expected reason?
- Are assertions meaningful?
- Does the test observe public behavior rather than private implementation?
- Are relevant failure paths included?
- Is the selected test boundary appropriate?
- Are mocks replacing the dependency that the test claims to validate?
- Is setup isolated from user data and other tests?
- Does the test contain hidden ordering or platform assumptions?
- Does it duplicate existing tests without adding evidence?
- Is the test name consistent with what it actually asserts?
- Does the expected result come from a confirmed requirement?
- Is the AI inventing an API or business rule?

Explain the risk of correlated mistakes when the same AI generates both the
implementation and the tests.

The developer should compare both outputs with the original requirement rather
than comparing only the code with the generated tests.

## Section 6.4 — Detecting Weak Assertions

Explain weak assertions such as:

```ts
expect(result).toBeDefined();
expect(command).not.toThrow();
expect(exitCode).toBe(0);
expect(mock.save).toHaveBeenCalled();
```

Explain why each may be insufficient when used alone.

Show how to strengthen assertions by checking the smallest meaningful evidence,
for example:

- normalized title
- initial `open` status
- exact ticket identity
- relevant error category
- whether storage was modified
- valid JSON content
- preservation of unrelated records
- standard output or standard error semantics
- process success or failure semantics
- absence of a false success message

Do not recommend asserting every internal field or every formatting character.

Include one concise conceptual before-and-after example:

```text

→ Human review
→ Strengthened test
```

The example must remain conceptual and unexecuted.

## Section 6.6 — Tests Do Not Prove Complete Correctness

Explain that passing tests provide scoped evidence only.

Discuss limitations such as:

- tests cover selected examples
- assertions may be weak
- requirements may be misunderstood
- important cases may be missing
- test and implementation may share the same defect
- mocks may differ from real dependencies
- environment and platform behavior may vary
- tests may not cover security, usability, performance, or operational risks
- a regression suite can become stale
- high test count or code coverage does not prove requirement correctness

Keep this consistent with existing reference `R-013`.

Explain that tests should complement:

- human review
- static analysis and type checking
- source verification
- exploratory testing
- integration and E2E testing
- security review where relevant
- measurement of real execution behavior
- clarification of ambiguous requirements

Do not claim that tests are ineffective. Explain both their value and their
limits.

## Section 6.7 — Recommended AI-Assisted Development Workflow

Create a practical workflow for future Week 2 implementation.

Use a sequence similar to:

```text
1. Clarify one behavior
2. Define acceptance evidence
3. Ask AI to propose a focused test
4. Review and correct the test
5. Observe expected Red
6. Ask AI for the smallest implementation
7. Review the code before accepting it
8. Run the focused test
9. Run regression tests
10. Add integration or E2E evidence where the risk crosses a real boundary
11. Refactor while tests remain green
12. Record assumptions, corrections, and remaining risks
13. Commit only reviewed and validated changes
```

For every step, briefly explain:

- what the AI may assist with
- what the developer must verify
- what evidence should be recorded

Include a concise table with columns such as:

| Step | AI contribution | Human responsibility | Evidence |
| --- | --- | --- | --- |

The workflow must reflect:

- TDD
- critical thinking
- layered testing
- human accountability
- validation of both AI-generated implementation and AI-generated tests

Do not claim that AI autonomously approves or validates its own final output.
